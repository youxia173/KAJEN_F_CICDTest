先读：CI/CD 到底是什么？（大白话）

把它想成工厂流水线，不是一种芯片技术，也不是再发明一种灯光协议。

你们现在写灯的固件，大概是：改代码 → 自己电脑编译 → 烧录板子测试 → 觉得 OK 了，把文件发给宜家。 CI/CD 就是把「检查、编译、打包、交给宜家」尽量变成自动的，少靠人工记得去做。

CI（持续集成）—— 自动质检

代码一推到 GitHub（或提合并请求），电脑自动帮你做检查，例如：

  • 代码风格乱不乱
  • 有没有明显低级错误
  • （以后）能不能编译出固件

就像：东西进仓库前，先过一道自动安检。安检不过，就提醒你改；过了，才继续往下。

你们项目里已经接上的，主要是这道安检（lint / cppcheck）。

CD（持续交付/部署）—— 自动出货

检查通过后，再自动：

  • 打一个版本号（比如 v0.3.3）
  • 打包固件
  • （宜家要求）上传到他们的升级服务器（OTA）

就像：质检合格后，自动装箱贴标签发货，不用每次纯手工拷文件。

这一块还没完全接通，因为需要宜家的上传接口和账号。

和宜家有什么关系？

宜家不是要你改灯的开关逻辑，而是要求：

供应商的固件开发，要走正规的「自动检查 + 可追溯发版」流程，代码放在 GitHub 上。

所以「按宜家规范做 CI/CD」≈：

别只靠工程师本机；要让 GitHub 也能自动检查，发版要有版本号和记录，最后能交到宜家系统。

你真正需要关心的，其实就 4 件事

清单很长，是因为合规细节多。对你个人，先记住这 4 步就够：

1. 代码放 GitHub仓库你们已经有了
2. 推上去看 Actions每次改完，看自动检查绿没绿
3. 发版打 Tag例如 v0.3.3，留下版本记录
4. 以后自动上传宜家给接口后，再接到他们的 OTA

其他像 Secrets、Variables、self-hosted runner、Docker……都是为了让第 2、4 步在云端也能跑，属于「环境配套」，不是灯功能本身。
